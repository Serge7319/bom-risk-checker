# One-time BOM report rollout

This offer uses Cadivor's existing BOM Analyzer and Reports workspace. A verified report-only account uploads and runs one BOM with up to 100 unique components, sees its exact size, then pays the active one-time price to unlock the complete saved report and standard PDF/CSV files. No full report is shown before payment, and the purchase does not start a subscription. The free anonymous audit at https://www.cadivor.com/#/analyze remains free and separate.

**Code deployment is safe with the offer disabled.** The offer requires `CADIVOR_ONE_TIME_BOM_ORDERS_READY=true` (after the SQL migration), `CADIVOR_ONE_TIME_BOM_REPORT_ENABLED=true`, `STRIPE_ONE_TIME_BOM_REPORT_PRICE_ID=price_...`, and the server-side `SUPABASE_SERVICE_ROLE_KEY`. Both flags default to off. Before checkout, the Analyzer verifies and shows the active nonrecurring Stripe price. Over-limit BOMs and unavailable prices cannot start checkout.

Turning the flag off stops **new** checkouts. Existing paid credits remain redeemable while the service-role database connection is available.

## Cadivor customer journey prepared in the app

- A signed-in account whose trial has ended or whose subscription is inactive can start in **BOM Analyzer** from **One-time report**, **Compare plans**, **Settings → Billing**, or **BOMs → New analysis**. After email verification, the buyer uploads and runs a BOM first. **Analyze a BOM free** remains a separate anonymous five-line audit.
- After the analysis finishes, the buyer sees the exact unique-component count and active Stripe amount before Checkout. A browser return alone never grants access; the signed webhook must mark the private order paid. The Analyzer checks payment automatically and saves/opens the report as soon as the webhook confirms it.
- A report-only BOM with more than 100 unique components is blocked before supplier lookups and payment. For an eligible BOM, the Analyzer runs the analysis but keeps all risk findings and downloads hidden until payment. The example-BOM action stays disabled for report-only accounts.
- **Settings → Billing → Single BOM reports** shows pending, paid, in-progress, completed, or refunded order status. Completed orders link only to a saved report that still exists in the workspace. Order history remains available if the sales flag is turned off.

**Public visitor entry:** `https://www.cadivor.com/#/one-time-report` offers a report-only account handoff and a separate sign-in link. The account includes no free-trial analyses. Its intent and **BOM Analyzer** destination survive Supabase email confirmation; the visitor uploads and runs a BOM, then sees the exact unique-component count and active Stripe price before Checkout. The report stays hidden until webhook-confirmed payment. If migration, feature flags, service key, or active nonrecurring price are missing, the app blocks the one-time offer. The inquiry form remains available for questions. A one-time purchase does not promise continuing monitoring.

## Preconditions before enabling a test purchase

1. Confirm the **existing** Stripe subscription webhook is working in a Stripe sandbox. `supabase/functions/stripe-webhook/index.ts` is versioned source; the repository's deployment notes say it has **not** replaced the live exported function. Do not assume merging this PR deploys it. The existing live destination must safely ignore `mode=payment` Checkout events, or it will retry every one-time payment as a missing subscription.
2. Inspect the live `stripe_webhook_events` schema. If the lease RPCs from `supabase/migrations/20260912_stripe_webhook_event_lease.sql` are not installed, review and apply that earlier migration first. It deliberately refuses to invent a missing live table. Verify normal Starter/Professional/Business checkout and renewal in sandbox afterward.
3. In the same Supabase project, run `supabase/migrations/20261004_one_time_bom_reports.sql` in SQL Editor. Confirm `public.users.id`, `public.analyses.id`, and `public.analyses.user_id` are UUID columns before applying. The migration creates private orders and service-only atomic fulfillment/reserve/consume RPCs. No anonymous or authenticated PostgREST role can read or write the order table. Set `CADIVOR_ONE_TIME_BOM_ORDERS_READY=true` on the corresponding Railway service after this migration succeeds; leave the sales flag off.
4. Deploy the versioned `stripe-webhook` function to a **sandbox** Stripe destination with its existing secret/JWT settings. Subscribe that destination to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, and `checkout.session.expired`, plus the existing subscription/invoice events. The function must receive the correct sandbox `STRIPE_WEBHOOK_SECRET`, `STRIPE_SECRET_KEY`, `SUPABASE_URL`, and `SUPABASE_SERVICE_ROLE_KEY`. Keep production configuration off while testing.
5. Create a **one-time, nonrecurring USD** Price in Stripe test mode. Set its `price_...` ID in Railway staging as `STRIPE_ONE_TIME_BOM_REPORT_PRICE_ID`; set `CADIVOR_ONE_TIME_BOM_REPORT_ENABLED=true` only there. Finance must decide the amount and any refund/tax policy. The code does not hardcode a price.

## Sandbox acceptance test

1. In a signed-out window, click **Analyze a BOM free** on the homepage. Expect the anonymous audit, never Stripe checkout. Then open **Get one full BOM report** and create a report-only account. Verify the email and continue to **BOM Analyzer**. Confirm the new profile has no trial entitlement or paid credit. Upload and run a BOM within 100 unique components; verify the exact count and active price appear before Checkout and that no report details are visible until the webhook confirms payment.
2. After analysis, inspect the paywall: only the unique-component count and active one-time price may be shown. Open Stripe Checkout and pay with a Stripe test card. The report tab should unlock automatically after the webhook confirms payment; no refresh is needed. In Supabase, check the private order moves `pending → paid`, with `stripe_session_id` and `payment_intent_id`. A browser return alone must never mark it paid.
3. For an eligible BOM, the app automatically saves the analysis only after the webhook confirms payment, then opens **Analysis Details**. **Reports** must provide the standard PDF and CSV packages. The order moves `paid → reserved → consumed` and stores the matching `analysis_id`.
4. Upload a BOM with 101 distinct MPNs. The one-time path must block analysis and checkout before supplier lookups and state that no payment was requested. Reduce it to 100 and confirm it can be analyzed.
5. A paid-credit analysis that is canceled or fails during persistence must safely return its order from `reserved` to `paid` when no saved analysis exists. An interrupted reservation may be recoverable after four hours. A report-only user who has not paid must not have a saved analysis or report visible.
6. Repeat the paid event delivery, then deliver an unpaid `checkout.session.completed` and a failed delayed payment in sandbox. Only a paid event for the same stored order, Stripe Session, user, and Price can grant a credit. Existing subscription checkout must still activate only its subscription plan.
7. Sign into a different account and confirm it cannot see, reserve, or consume the first account's purchase or saved BOM. Check the order table is unreadable with the anon and authenticated API keys.
8. In **Settings → Billing**, confirm the paid order says **Report ready** after payment and opens the correct saved BOM in Reports. Pause new sales with the feature flag and confirm this order remains visible and its report remains accessible. Verify another signed-in account sees only its own orders. The Stripe subscription portal must remain separate from the one-time order list.

After this passes in sandbox, deploy the webhook to the live destination under the normal release procedure, configure the live nonrecurring Price, repeat one controlled live purchase and report retrieval, then enable the Railway production flags. The marketing CTA already routes into the direct signup flow, but its app entry remains closed while the required production configuration is off. Advertise the report as immediately purchasable only after the public route, live price, paid fulfillment, and report retrieval are verified. Never share Stripe keys, webhook secrets, customer BOMs, or sign-in links in a support message.

## Operational notes

- The webhook is the only grant path. Duplicate events return an idempotent outcome. A pending session can be reopened; a completed session awaiting the webhook cannot trigger a second purchase from the page.
- A full saved analysis consumes its credit after component records are written. Reports remain accessible under the existing saved-work policy when a trial ends.
- A failed save after its summary is created attempts to remove the incomplete summary and restore the credit. If database reconciliation fails, the user sees a support error and the private order remains auditable.
- Orders contain IDs and status, not a copy of the BOM. The existing saved BOM workspace owns the analysis data and its access policy.
- The Billing order list is an in-app purchase record, not a Stripe invoice or tax receipt. Stripe's test/live payment records remain the financial source of truth. The refund decision and any customer receipt workflow require finance policy before launch.
